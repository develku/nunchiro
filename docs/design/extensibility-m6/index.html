다른 사람이 Nunchiro 위에 만들 수 있게: 공개된 API, 플러그인 폴더, 틀 만들기 명령, 목록, 바깥에서 거는 시작

점수표 p36(다른 사람을 위한 확장성)은 지금 10점입니다. 플러그인 API, 틀 만들기 명령, 목록, 바깥에서 거는 시작이 없고, 소켓 형식도 공개돼 있지 않습니다. 아래는 세 가지 안과 추천안의 화면입니다. 새 문구는 영어만 적었습니다.

추천: B, 다섯 번에 나눠 만들기
  1. API 형식을 공개합니다. 코어의 타입에서 JSON Schema를 만들어 저장소에 두고, 타입이 바뀌면 테스트가 실패합니다. herdr 방식입니다.
  2. 플러그인은 폴더 하나입니다. plugin.toml 한 장이 패널, 명령, 설정, 막기(gate), 스킬, 훅, MCP 서버를 묶습니다. 패널과 스킬은 지금 있는 위젯과 확장 항목을 그대로 씁니다.
  3. 플러그인 코드는 창 안에서 돌지 않습니다. 지금 위젯처럼 샌드박스 안의 명령으로 돌고, 사용자가 내용을 보고 승인해야 켜집니다.
  4. 바깥에서 거는 시작은 예약의 한 종류입니다. 때가 시각이 아니라 사건입니다. GitHub는 사용자의 gh로 읽고, 그 밖의 서비스는 이 Mac의 주소로 받습니다. Nunchiro 서버는 두지 않습니다.
  5. 목록은 고정된 저장소 하나입니다. 테마 고르기와 같은 길로 읽고, 받은 파일의 해시가 목록과 다르면 설치하지 않습니다.

A. 공개만: API 스키마와 문서

코어 소켓의 요청과 응답을 스키마로 내고, 문서 한 장과 돌아가는 예제를 둡니다. 플러그인, 목록, 바깥 시작은 만들지 않습니다. B의 첫 PR이 바로 이것입니다.

Local API

Nunchiro's background service listens on a unix socket in its data folder. Each request is one line of JSON, and so is each reply. The CLI, the MCP server and the window all use it.

Who you are

Without a token you act as the owner. With a token from nunchiro token create you act within its scope: read, supervised or full.

What is stable

Operations marked stable in the schema keep their shape within a major version. The rest belong to the window and may change in any release.

얻는 것
  • XO5가 "예"가 됩니다. p24(인터페이스)의 I4도 같은 이유로 "반"이었으니 함께 오릅니다.
  • 스키마는 코드에서 만들어지므로 문서가 코드와 어긋날 수 없습니다. 어긋나면 테스트가 빨갛게 됩니다.
약점
  • p36은 다섯 줄 가운데 한 줄만 채워 20점쯤입니다.
  • 요청이 189가지인데 대부분 창 전용입니다. 그래서 stable 표시를 붙여, 남이 기대도 되는 것과 아닌 것을 가릅니다. 토큰이 부를 수 있는 것(지금 문서의 "Outside callers" 표)만 stable입니다.

B. 플러그인 = 폴더 하나 추천

A에 더해, ~/.nunchiro/plugins/<id>/ 폴더와 plugin.toml 한 장을 플러그인으로 정합니다. 새 실행 방식은 만들지 않습니다. 패널은 지금의 위젯, 스킬·훅·MCP는 지금의 확장 항목이고, 명령·설정·막기만 새로 생깁니다.

플러그인의 모양 · 예제 "Quiet hours": 밤에는 에이전트와 예약이 새 세션을 시작하지 못하게 합니다

# ~/.nunchiro/plugins/quiet-hours/plugin.toml id = "quiet-hours" name = "Quiet hours" version = "0.1.0" about = "Holds new sessions that agents and schedules start at night." author = "you" nunchiro = ">=0.2" [[panel]] # a widget, exactly as widget.toml today name = "Held tonight" command = ["./quiet.sh", "panel"] interval_secs = 60 [[command]] # a row in the command palette name = "Pause quiet hours until tomorrow" command = ["./quiet.sh", "pause"] show = "note" # note | panel | send (to the focused agent) [[setting]] # a row under the plugin in Settings key = "from" label = "Quiet from" type = "time" default = "23:00" [[gate]] # may refuse or change an action on = "session.start.before" command = ["./quiet.sh", "gate"] on_error = "allow" skills = ["skills/quiet-hours"] # folders, as extensions today
정한 것
  • 일곱 가지를 묶습니다: panel, command, setting, gate, skills, hooks, mcp. 앞의 넷은 플러그인만 할 수 있고, 뒤의 셋은 지금도 따로 추가할 수 있습니다.
  • 명령은 배열입니다. 셸 문자열이 아닙니다. herdr도 같습니다. 폴더 밖의 파일은 실행하지 못합니다.
  • 샌드박스 안에서 돕니다. 지금 스크립트 위젯이 쓰는 실행기입니다. 네트워크는 목록에 적은 호스트만, 읽기는 플러그인 폴더와 적어 둔 폴더만 됩니다.
  • 승인이 있어야 켜집니다. 파일이 한 글자라도 바뀌면 다시 묻습니다. 에이전트는 승인할 수 없습니다.
  • 막기(gate)는 두 곳에서만: 새 세션 시작 전, 그리고 에이전트·예약·바깥 시작이 보내는 메시지 전. 사용자가 입력칸에 직접 쓴 글은 어떤 플러그인도 건드리지 못합니다.
  • 막기는 좁히기만 합니다. 권한 요청에 답하거나 외부 전송 카드를 건너뛰게 할 수 없습니다. 5초 안에 답이 없으면 on_error대로 합니다.
막기가 주고받는 것
stdin {"event":"session.start.before","asker":"agent", "session":{"kind":"claude","project":"/…/nunchiro"}, "settings":{"from":"23:00","to":"07:00"}} stdout {"allow":false,"reason":"Quiet hours until 07:00."}

타입
  • 플러그인은 TypeScript가 아니라 명령이므로, "타입"은 JSON Schema 두 장입니다: plugin.schema.json(매니페스트)과 API 스키마 안의 gate 입력·출력. 틀이 넣는 첫 줄 #:schema … 덕에 편집기가 자동 완성과 오류를 보여 줍니다.
  • plugin check는 승인 없이 샘플 입력으로 한 번 돌려 봅니다. 진짜 세션은 건드리지 않고, 위젯 검사와 같은 가둔 폴더에서 돕니다.
  • 에이전트도 이 명령으로 플러그인을 만들 수 있습니다. 승인은 여전히 사용자의 일입니다.

B의 넷째 조각: 바깥에서 거는 시작 (Triggers)

예약과 같은 것인데 때가 시각이 아니라 사건입니다. 무엇을 시작할지는 예약처럼 사용자가 미리 정한 닫힌 묶음(누가, 어느 폴더, 무슨 일)이고, 바깥에서 온 글은 지시가 아니라 인용된 자료로만 붙습니다.

세 가지 길
  • GitHub: 사용자의 gh로 2분마다 읽습니다. 지금 PR 실시간 확인이 쓰는 실행기 그대로입니다. 터널도 서버도 필요 없습니다. T3 Code가 이 방식입니다.
  • Webhook: 이 Mac의 127.0.0.1 주소 하나. 웹훅 트리거가 하나라도 있을 때만 열립니다. 서명이 맞지 않으면 버립니다. Slack·Linear처럼 인터넷에서 부르는 서비스는 사용자의 터널(Tailscale Funnel, cloudflared)이 있어야 닿습니다.
  • 명령: nunchiro trigger fire <name> --data @file. cron, CI, 다른 도구가 부릅니다. 새 토큰 범위 trigger는 이것 하나만 할 수 있습니다.
안전
  • 트리거는 사용자만 만듭니다. 에이전트는 예약처럼 제안 카드만 낼 수 있습니다.
  • 부르는 쪽은 무엇을 시작할지 정하지 못합니다. 이름을 부를 뿐입니다.
  • 같은 PR이나 이슈로는 겹쳐 시작하지 않습니다. 한 시간에 4번까지입니다.
  • 메모리 보류(M8), 외부 전송 카드, 권한 방식은 다른 세션과 똑같이 적용됩니다.
  • 기본은 Ask me first입니다.
하지 않는 것
  • Nunchiro가 운영하는 중계 서버. Orca는 자기 클라우드로 사건을 받습니다. Nunchiro는 서버가 없고 "아무것도 밖으로 보내지 않는다"가 약속이라 두지 않습니다.

C. 창 안에서 도는 코드 플러그인 (지금은 아님)

Orca, bb, Paseo의 방식입니다. 플러그인이 TypeScript로 쓰이고, npm으로 내는 SDK 타입을 쓰며, 패널은 창 안의 가둔 틀(iframe)에서, 뒤쪽 코드는 별도 프로세스에서 돕니다.

얻는 것
  • 패널을 마음대로 그릴 수 있고, 창의 사건에 바로 반응합니다.
  • Orca의 16가지 모양에 가까워집니다(파일 보기, 상태 막대 항목, 언어 강조).
드는 것
  • 창의 내부를 API로 굳혀야 합니다. 지금은 창을 자주 다시 설계하고 있어서(팀, 봇, 리드) 약속하기 이릅니다.
  • npm 패키지를 내고 버전을 지켜야 합니다. 새 공급망입니다.
  • Paseo는 플러그인을 가두지 않고, bb는 서버 프로세스 안에서 돌립니다. Orca만 틀과 지문 승인을 갖췄고 그 코드가 큽니다.
  • 웹 위젯(지금 있음)이 이미 "자기 HTML을 가진 패널"입니다. B의 panel이 kind = "web"을 받으므로, C의 큰 부분은 B에 들어 있습니다.

정할 질문

각 질문 아래가 추천입니다. 만들기는 승인 뒤에 시작합니다.

1. A, B, C 가운데 어느 것입니까?추천: B. PR 1이 A이고 혼자서도 나갑니다. C는 창 설계가 자리 잡은 뒤에 정합니다.
2. 플러그인이 동작을 막거나 바꿀 수 있게 합니까(gate)?추천: 예, 다만 새 세션 시작과 자동으로 보내는 메시지 두 곳만. 사용자가 직접 쓴 글은 건드리지 못하고, 사용자의 시작은 Start anyway로 넘깁니다. 다른 답: 막기 없이 패널·명령·설정만(그러면 XO1은 "반"으로 남을 수 있음).
3. 목록 저장소를 공개로 하나 만들어도 됩니까(develku/nunchiro-plugins)?추천: 예. 처음에는 Nunchiro가 만든 예제 서너 개만 넣습니다. 남의 플러그인을 받을지는 그 뒤에 정합니다(본 저장소는 지금 바깥 PR을 받지 않습니다). 새 공개 저장소를 만드는 일이라 사용자의 승인이 필요합니다.
4. 웹훅 주소를 엽니까?추천: 예, 127.0.0.1에만, 웹훅 트리거가 있을 때만. 인터넷에서 닿게 하는 터널은 사용자의 것이고 Nunchiro가 만들지 않습니다. 다른 답: GitHub 읽기와 명령만 내고 웹훅은 미룸(XO4는 그래도 참일 가능성이 큼).
5. 트리거의 기본은 Ask me first입니까?추천: 예. 스스로 시작은 트리거마다 사용자가 켭니다. 한 시간 4번 한도는 그대로 둡니다.
6. p22의 넓이를 세는 줄을 늘립니까?추천: 지금은 아니오. 줄을 늘리면 점수표가 엄격해지고(Orca의 모양 가운데 없는 것이 "아니오"로 잡힘) 먼저 내려갑니다. M6를 다 만든 뒤 주간 검토에서 정합니다. 점수를 올리려고 기준을 느슨하게 하는 안은 없습니다.
