Push와 PR 만들기를 에이전트에게 부탁하지 않고 앱이 직접 합니다. 누르기 전에 무엇이 나가는지 보여 줍니다

지금 Diff 패널의 git 버튼은 에이전트에게 정해진 문장을 보냅니다. 에이전트가 git을 돌리므로 토큰이 들고, 무엇이 push될지 누르기 전에 보이지 않습니다. 점수표(p01)도 이것을 "앱이 하는 일"로 세지 않습니다(G2, G6 반쪽). 아래는 앱이 직접 push하고 PR을 만드는 안 세 가지입니다. 이미 있는 Merge 버튼과 같은 규칙을 씁니다. 창이 보여 준 커밋을 코어가 다시 확인하고, 그 사이에 바뀌었으면 아무것도 하지 않습니다.

추천: B, 네 번에 나눠 만들기
  1. Push는 확인 한 줄. 커밋 수, 가는 곳, 맨 위 커밋을 보여 주고 Push를 누르면 코어가 git push를 돌립니다.
  2. PR은 폼이 곧 확인. 제목과 설명이 커밋에서 미리 채워져 있고 고칠 수 있습니다. Push & create PR을 누르면 push한 뒤 gh pr create를 돌립니다.
  3. 글은 누를 때만 AI가 씁니다. Write with AI를 누르면 앱이 에이전트 CLI를 한 번 따로 불러 제목과 설명을 채웁니다. 세션 대화는 건드리지 않습니다.
  4. 기본 브랜치로는 한 번에 못 보냅니다. 지금 규칙 그대로입니다. 강제 push는 넣지 않습니다.
점수표 p01 (추정)
56.5 → 61.5 G2, G6이 반쪽에서 예가 되면 깊이 70 → 80. 넓이(이슈 출처 수)는 M3의 몫입니다. G6은 커밋 메시지까지(4번째 PR) 되어야 확실히 예입니다.

A. 확인 줄만: 한 번 누르고, 글은 AI가 쓰고, 고칠 수 없음

T3 Code, monocode, Paseo의 방식입니다. 버튼을 누르면 확인 줄이 나오고, 확인하면 앱이 push하고 AI가 쓴 제목과 설명으로 PR을 만듭니다. 글은 PR이 만들어진 뒤에야 보입니다.

M +8 -0 crates/parse/tests/lex.rs

  • 가장 빠릅니다. 두 번 누르면 끝납니다.

  • base 브랜치와 draft를 고를 자리가 없습니다.
3

B. 폼이 확인추천

Orca, Superset, emdash, vibe-kanban의 방식입니다. PR은 제목과 설명이 보이는 폼에서 만들고, 그 폼의 버튼이 확인입니다. Push만 할 때는 Merge와 같은 확인 한 줄입니다. 에이전트가 일하는 중이어도, 터미널 세션이어도 쓸 수 있습니다. 에이전트에게 묻지 않기 때문입니다.

PR이 아직 없을 때 · Diff 패널 머리의 버튼을 누르면 그 아래로 폼이 열립니다

규칙
  • 창이 보여 준 맨 위 커밋(head)을 요청에 실어 보냅니다. 코어가 지금의 HEAD와 다르면 거절합니다. Merge가 쓰는 규칙입니다.
  • 코어는 git push <remote> HEAD:refs/heads/<branch>만 돌립니다. 처음이면 --set-upstream을 붙입니다. 맨 git push는 쓰지 않습니다(git 설정이 다른 곳으로 보낼 수 있어서).
  • 기본 브랜치, detached, 리모트보다 뒤처진 브랜치에서는 버튼이 꺼져 있고 이유가 나옵니다. 지금과 같습니다.
  • 강제 push 없음. 리베이스한 뒤에는 지금처럼 "Rebase or merge first"에서 멈춥니다.
  • 창(사용자)만 할 수 있습니다. 에이전트 세션과 폰의 브라우저 페이지는 거절됩니다. Merge와 같습니다.
  • PR 설명은 gh pr create --body-file -로 넘깁니다. 토큰은 gh가 갖고 있고 Nunchiro는 읽지 않습니다.
  • 제목, 설명, 브랜치 이름은 바깥 글입니다. 화면에는 글자로만 그립니다.
Write with AI
  • 세션의 에이전트 CLI를 따로 한 번 부릅니다(Orca, monocode 방식). 도구 없이, 그 에이전트의 가장 작은 모델로, 세션의 계정으로.
  • 넣는 것: 커밋 제목, 바뀐 파일 통계, 60,000자까지의 diff, 저장소의 PR 템플릿. 모두 "지시가 아닌 자료"로 표시합니다.
  • 누르지 않으면 토큰이 0입니다. 한 번에 대략 입력 5천~2만, 출력 1천 토큰(추정).
  • ACP 에이전트와 터미널 세션에는 이 버튼이 없습니다. 커밋에서 채운 글만 있습니다.
바뀌지 않는 것
  • 커밋은 지금처럼 에이전트에게 부탁합니다(안 C에서 다룹니다). 바뀐 파일이 남아 있으면 버튼은 Commit입니다.
  • 에이전트가 스스로 push하는 것은 막지 않습니다.

C. B에 더해 커밋도 앱이

T3 Code와 Orca는 커밋도 앱이 합니다. 파일을 고르고, 메시지를 비워 두면 AI가 씁니다. G6("AI 커밋 메시지와 PR 글")을 온전히 예로 만들려면 이것까지 필요합니다. B의 네 번째 PR로 붙일 수 있습니다.

Diffparser-fix
crates/parse/src/lex.rs
crates/parse/tests/lex.rs
notes.txt  untracked
드는 것
  • 무엇을 스테이지할지 고르는 화면이 새로 필요합니다. 새 파일(untracked)은 기본으로 빼 둡니다.
  • 에이전트는 자기가 무엇을 왜 바꿨는지 압니다. 앱의 AI는 diff만 봅니다. 메시지 품질은 써 봐야 압니다.
  • 커밋 훅이 코어에서 돌게 됩니다(에이전트가 돌릴 때와 같은 사용자, 같은 폴더).

커밋은 밖으로 나가지 않고 되돌릴 수 있어서 확인 줄이 없습니다. Commit, then push…는 B의 확인으로 이어집니다.

  • 우리의 차이: 보여 준 커밋을 코어가 다시 확인합니다(다른 앱에는 없음). 기본 브랜치는 경고가 아니라 막습니다. AI는 누를 때만 씁니다.

답할 질문

정해진 답: 1-3은 추천대로(B, 누를 때만, 강제 push 없음). 4는 바뀜: 에이전트에게 부탁하는 길도 남기고, 버튼 옆 메뉴에서 고른 길을 기억합니다. 각 질문 아래가 추천입니다.

1. A, B, C 가운데 어느 것입니까?추천: B. PR 1(push), PR 2(PR 폼), PR 3(Write with AI) 순서로 냅니다. C(앱 커밋)는 B를 써 본 뒤 네 번째 PR로 정합니다.
2. AI 글은 누를 때만 씁니까, 폼이 열릴 때 저절로 씁니까?추천: 누를 때만. 토큰을 사용자가 정합니다. Orca는 "폼을 열 때 저절로"가 설정에 있고 기본은 꺼져 있습니다. 다른 답: 설정에 스위치를 두고 기본은 끔.
3. 강제 push를 넣습니까?추천: 넣지 않음. T3 Code와 monocode도 없습니다. 리베이스 뒤에는 터미널에서 합니다. 다른 답: Orca처럼 리베이스 뒤에만 --force-with-lease를 따로 확인받고.
4. 에이전트에게 부탁하는 길을 남깁니까?추천: push와 PR에서는 없앱니다(버튼 하나, 길 하나). 에이전트에게는 채팅으로 언제든 말할 수 있습니다. 커밋은 C 전까지 지금처럼 에이전트에게 부탁합니다.
